1.3 Lab deviation: a solid-state 3D LiDAR in place of the 2D lidar

The V1.0 design gives the Least-Cost branch a single-plane 2D lidar (rank 5, optional). The lab has a solid-state 3D LiDAR available now, so the S32Z2 island uses it in that slot. This is a deviation of the implementation from the design, recorded here; the released design is unchanged.

What does not change. The lidar keeps its rank-5 role exactly (§6.2, §9.4 rung E): it is optional, it may confirm or disqualify (a refuge, a corridor, free space) and add hazards, and it may never qualify a refuge, supply a corridor, or lift a blackout. It "adds confidence, never capability". Therefore the island ODD claim stays as §9.5 states it: city-road class, about 30 km/h, fair weather. A 3D lidar loses range in fog and spray together with the camera, as the 2D one does.

What changes, node by node.

Node With the 2D lidar (design) With the 3D LiDAR (this plan)
N13 scan guard ~1080 points per scan, planar occupancy Crop to the ego corridor and near field, ground segmentation, voxel downsample to a fixed-capacity PointCloud2; free-space distance ahead, nearest in-path return, kerb height and position
I19 AEB Planar returns: a low or overhanging obstacle can be missed Height-resolved returns: fewer ground false positives, catches low and overhanging obstacles
I20 collision detector Planar near field 3D near field, limited by the LiDAR's minimum range and field of view; the ultrasonics still guard the last metre
N16 world model Confirming channel Same role, richer confirmation
N18 pull-over Confirms the physical edge Confirms the edge and measures kerb height, which can disqualify an unsafe refuge
N19 ODD monitor Lidar-vs-camera divergence; return range and intensity Same test with more returns per frame; multi-echo if the sensor provides it
N22 B5 stream Planar scan Downsampled cloud only, within the stream's bit-rate bound

What it costs on the S32Z2. A 2D scanner delivers about 43 k points/s (1080 × 40 Hz). Solid-state 3D LiDARs typically deliver 10^5 to several 10^5 points/s, at tens of Mbit/s over Ethernet. That moves N13 from about 5 Mop/s (§9.5) to the largest P2 load after N14, and its frame buffer to roughly a megabyte or more of the 19 MB SRAM. N13 must reduce each frame to its fixed output bound inside its P2 period, and Q9 below has to be answered before WP5 sizes it.

What it could enable later (not taken here). A 3D LiDAR's forward range would cover the 43 m stopping distance at 60 km/h that §9.5 says a low-cost 2D lidar cannot. Using that to raise the Least-Cost v_odd would make the lidar a capability, which contradicts its rank-5 role; it is a design change for the WG, not something this plan assumes.

2. Dependencies among the nodes

2.1 Source and method

Every edge comes from the edge catalogue in messageflow/L4SafetyIsland-MessageFlow.md (§3, tables A–F, and the E / V badges), restricted to this platform: N6 removed, N13 kept, I15 dropped. An edge u → v means v consumes a message u produces. Taken literally, 24 of the island's nodes form a single cycle. The vehicle closes the loop (I1 → I16 → N4 → I9 → I1), and every behaviour reports its status back to the node that commanded it. To get a build order, the plan separates two kinds of edge:

  • Forward edges: a node needs this input to do its job. They set the order.
  • Feedback edges: the actuator command path (I1 → I16, I1 → N9) and the status and acknowledgement replies (N7 → N3, N5 → N3, N18 → N3, N18 → I7, I6 → I7, N10 → N2, N18 → N19, N3 → N5, N3 → N21). Node tests stub them, and only integration closes them.

2.3 What the dependency structure means for the plan

  1. The hubs are built interface-first. I1 (12 command sources) and N8 (11 fault sources) sit at the bottom of the order, but every behaviour needs them. Each is built early, with all of its ports declared, and the ports are filled as producers arrive. An unconnected I1 port is a source that never wins arbitration. An unconnected N8 source is a row in the fault table with no producer yet. Neither blocks the other work packages.
  2. The message definitions are everyone's dependency. Every edge is a typed topic, so autoware_safety_island_msgs (Part 3 of the design) and the E2E profiles come before any node: WP0.
  3. The B4 path is a closed sub-graph at the root of the order. The nine nodes N4 N3 N8 N17 I7 I6 I1 I16 I5 consume no exteroceptive topic. Only N17's camera-validity verdict reaches them, through N8. They are therefore built and demonstrated first (WP2–WP3). Every later WP adds capability above a floor that already works.
  4. Sensing is a parallel track. N13–N17 and N16 sit at L0–L1 with no dependency on P0, as §12 of the design notes. WP5 runs alongside WP2–WP4 and joins at N8, N3, N5 and N7.
  5. Behaviours are built in dependency order, not number order. B2 needs N5, which needs the camera corridor (N14, N16). B3 needs N18 and the B2 machinery in N7. B1 needs N19, which needs the sensing chain. So the order is B4 → B2 → B3 → B1, then B6 and B5.

3.4 Minimal pull-over island

§9.4 and §12 recommend the shortest path to a demonstrable L4 fallback: phases 1, 3 and 4 reduced to their mandatory nodes, deferring the guardian role. On S32Z2 that is WP2 + WP3 + WP4 (N7, I13, I9/I11/I12) + WP5 + WP7 (N18), which delivers D1 and D3. It is 21 mandatory nodes with N13 in place of N6, plus the 3 recommended. WP6's B2 hold and WP8's guardian role (I8, N10) can follow.
